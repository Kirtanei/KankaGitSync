# Kanka Git Sync — Project Ruleset v0.1

## 1. Purpose

The project provides bidirectional synchronization between a Git-managed worldbuilding repository and a Kanka campaign.

The intended division of responsibilities is:

* **Git** provides permanent history, branching, diffs, review, IDE access and the canonical record of accepted changes.
* **Kanka** provides the web interface used by the GM and players.
* **Both Git and Kanka are valid editing surfaces.**
* Changes made by players in Kanka must never be silently lost or overwritten.
* Changes made by the GM in either Git or Kanka should be distinguishable from player changes.
* Kanka-specific implementation details must not become fundamental to the world's underlying data model.

Kanka explicitly supports integrations that read, modify and synchronize campaign data with another service. Its API operates on live campaign data and does not provide a server-side dry-run mode.

---

# 2. Normative terminology

The words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** describe project requirements.

The following terms are used throughout:

**LOCAL**
: The accepted world state represented by the Git `main` branch.

**REMOTE**
: The current state of the Kanka campaign.

**KANKA LIVE**
: The Git representation of REMOTE, stored on the generated `kanka/live` branch.

**OWNER**
: The GM or other explicitly configured Kanka users whose changes are considered owner changes.

**PLAYER**
: A Kanka campaign member who is not configured as an OWNER.

**SYNC ACTOR**
: Changes performed through the Kanka API by this synchronization tool.

**RESOURCE**
: An independently synchronized unit, such as an entity, post, property or relation.

---

# 3. Fundamental architecture

The repository SHALL use this conceptual model:

```text
                         Players
                            │
                            ▼
                         Kanka
                            │
                         fetch
                            │
                            ▼
                     kanka/live
                          Git
                         branch
                            │
                       review/merge
                            │
                            ▼
                          main
                            │
                       local edits
                            │
                            ▼
                          push
                            │
                            ▼
                         Kanka
```

`main` and Kanka SHALL NOT be compared directly.

`kanka/live` SHALL represent the last Kanka state observed by the synchronizer.

This means that Git itself provides most of the three-way synchronization model:

```text
merge-base(main, kanka/live)
            │
       ┌────┴────┐
       ▼         ▼
     main     kanka/live
    LOCAL       REMOTE
```

The synchronizer SHOULD rely on normal Git history wherever possible rather than implementing an independent version-control system.

---

# 4. Authority model

Git SHALL be the **authoritative history**, but not the only authorized editing interface.

Kanka SHALL remain writable by campaign members.

The following rules apply:

| Change source                 | Treatment                                       |
| ----------------------------- | ----------------------------------------------- |
| GM changes in Git             | Local authoritative change awaiting publication |
| GM manual changes in Kanka    | Valid remote owner change                       |
| Player changes in Kanka       | Valid remote player contribution                |
| Synchronizer changes in Kanka | Mirror of an already-known Git operation        |
| Unknown Kanka user            | Untrusted remote contribution requiring review  |

A player change MUST NOT automatically lose to a Git change merely because Git is considered authoritative history.

"Authoritative history" means that once a change has been accepted, Git is where its permanent historical record resides.

---

# 5. Git branches

The minimum branch structure SHALL be:

```text
main
kanka/live
```

## `main`

`main` represents the accepted version of the world.

Normal authoring, AI-assisted editing and feature branches SHALL ultimately merge into `main`.

## `kanka/live`

`kanka/live` represents the most recently fetched Kanka state.

It MUST be generated by the synchronizer.

Humans MUST NOT manually edit or commit directly to `kanka/live`.

A fetch from Kanka modifies `kanka/live`, never `main`.

This allows:

```bash
git diff main..kanka/live
```

to display outstanding differences between the accepted world and Kanka.

And:

```bash
git log main..kanka/live
```

to display remote Kanka changes not yet integrated into `main`.

---

# 6. The core safety invariant

**A push MUST begin with a fetch.**

No command may perform:

```text
Git → Kanka
```

without first establishing the current Kanka state.

The required push sequence is:

```text
1. Fetch current Kanka state.
2. Update kanka/live.
3. Determine whether kanka/live contains unintegrated remote changes.
4. Abort if unintegrated changes exist.
5. Validate LOCAL.
6. Calculate the proposed Kanka operations.
7. Display or record the operation plan.
8. Apply the changes.
9. Fetch Kanka again.
10. Verify that REMOTE matches the expected normalized state.
11. Advance kanka/live.
```

This rule exists primarily to protect player edits.

---

# 7. Push blocking rule

A push MUST be rejected whenever `kanka/live` contains changes that are not represented in `main`.

For example:

```text
main
 A──B──C
     \
      D──E  kanka/live
```

A push is prohibited because `D` and `E` represent changes made in Kanka which have not been reconciled.

The user must first merge, modify, or explicitly reject those changes.

After reconciliation:

```text
main
 A──B──C──F
     \   /
      D─E    kanka/live
```

changes unique to `main` may be published.

The system MUST NOT provide a normal "force push" workflow that casually bypasses this protection.

---

# 8. Player changes

Player-created and player-edited content SHALL be considered legitimate remote input.

A player does not require:

* Git access;
* knowledge of the repository;
* a GitHub account;
* an IDE;
* knowledge of the synchronization system.

Their workflow remains:

```text
Kanka
  ↓
Edit
  ↓
Save
```

The next Kanka fetch SHALL preserve that change on `kanka/live`.

A player change MUST NOT be automatically merged into `main` unless the user has explicitly configured such a policy.

The default behavior SHALL be:

```text
Player edit
   ↓
kanka/live
   ↓
visible in status/diff
   ↓
GM review
   ↓
merge into main OR deliberately reject
```

---

# 9. Owner changes made directly in Kanka

Changes made manually in Kanka by an OWNER are valid changes.

They SHALL still pass through `kanka/live`.

The synchronizer MAY offer automatic integration of owner-only changes when:

* `main` is clean;
* no conflicting local edit exists;
* the resource can be merged losslessly.

The default implementation SHOULD nevertheless preserve an audit trail rather than modifying `main` invisibly.

---

# 10. Identifying Kanka authors

Kanka entities expose `created_by` and `updated_by`, and entities can be filtered by those user IDs. Campaign membership endpoints expose campaign user IDs and names. Posts and properties likewise expose creator/updater information.

The repository SHALL contain a non-secret mapping such as:

```yaml
users:
  12345:
    name: Jesper
    role: owner

  28191:
    name: Alice
    role: player

  33104:
    name: Bob
    role: player
```

Unknown IDs SHALL default to:

```yaml
role: unknown
```

Unknown users SHALL receive the same overwrite protection as players.

---

# 11. Git authorship

The synchronizer MUST NOT invent player email addresses.

Unless a player has explicitly configured a Git identity, imported commits SHOULD use a technical Git author such as:

```text
Kanka Sync <kanka-sync@localhost>
```

and retain actual provenance through commit trailers:

```text
Kanka-User: Alice
Kanka-User-ID: 28191
Kanka-Source: web
Kanka-Entity-ID: 91827
Kanka-Event-ID: 21321445435345346
```

If precise original authorship cannot be established, the synchronizer MUST say so.

It MUST NOT attribute a combined or ambiguous change to the last known editor merely because that is the only user ID available.

---

# 12. Webhook attribution

Premium Kanka campaigns can trigger webhooks for entry creation, modification and deletion. Payload webhooks contain the affected entry along with fields including `created_by` and `updated_by`.

When available, webhook events SHOULD be used to improve authorship and sequencing.

Conceptually:

```text
Alice saves Kanka entry
        ↓
     webhook
        ↓
event stored
        ↓
fetch exact resource
        ↓
commit to kanka/live
```

A webhook SHALL be considered a notification, not the sole source of truth.

The synchronizer MUST still be capable of fetching the actual Kanka state.

This is particularly important because Kanka's normal history does not track changes to every subordinate resource such as properties and articles/posts.

---

# 13. Polling fallback

The project MUST function without webhooks.

Without webhooks:

```text
kanka fetch
```

SHALL compare the current Kanka representation with `kanka/live`.

Attribution in polling mode is inherently less precise if several users modify the same resource between fetches.

Therefore:

* exact attribution SHOULD be retained when known;
* probable attribution MAY be recorded as such;
* ambiguous attribution MUST remain ambiguous.

Correct content preservation takes precedence over producing attractive Git authorship.

---

# 14. Detecting synchronization echoes

API requests operate as the authenticated Kanka user.

Consequently:

```text
git push
   ↓
synchronizer updates Kanka
   ↓
Kanka reports "updated by Jesper"
```

is indistinguishable by user ID alone from:

```text
Jesper manually edited Kanka
```

The synchronizer MUST therefore maintain an operation ledger for writes it performs.

The ledger SHOULD include:

```text
operation ID
resource ID
normalized before hash
normalized after hash
timestamp
Kanka response ID
webhook/event IDs already consumed
```

A remote change matching an expected synchronization result SHALL be classified as a synchronization echo.

A remote change from the same user that does not match a known synchronization operation SHALL be treated as a manual Kanka edit.

Recommended structure:

```text
world/
├── characters/
│   ├── prince-maximilian/
│   │   ├── index.md
│   │   ├── properties.yml
│   │   ├── relations.yml
│   │   └── posts/
│   │       ├── public-history.md
│   │       └── private-notes.md
│   │
│   └── ...
│
├── locations/
├── organisations/
├── quests/
├── items/
├── creatures/
├── journals/
├── tags/
└── ...

gm/
└── ...

.kanka/
├── config.yml
├── users.yml
└── ids.yml
```

`gm/` SHALL be local-only unless an explicit rule states otherwise.

---

# 16. Local entity identifiers

Every managed entity MUST have an immutable local identifier.

Example:

```yaml
id: prince-maximilian
name: Prince Maximilian
```

The identifier is not the display name.

Renaming:

```yaml
name: King Maximilian
```

MUST NOT require changing:

```yaml
id: prince-maximilian
```

Local IDs SHOULD remain understandable to humans while being unique within the repository.

Kanka database IDs MUST NOT be used as the canonical identity of world objects.

---

# 17. Kanka ID mapping

Kanka distinguishes between generic entity IDs and type-specific record IDs; generic entity responses expose fields such as `id`, `entity_id`/shared entity identity and `child_id` for the type-specific record.

Those implementation details SHALL live in the adapter layer:

```yaml
# .kanka/ids.yml

prince-maximilian:
  entity_id: 1842
  child_id: 901
  entity_type: character

tarant:
  entity_id: 381
  child_id: 204
  entity_type: location
```

Lore files SHOULD NOT need to know these numbers.

---

# 18. Local references

Repository content SHOULD reference stable local IDs:

```markdown
[[prince-maximilian]]
```

rather than:

```text
[entity:1842]
```

Custom display text MAY use:

```markdown
[[prince-maximilian|Maximilian]]
```

On publication, the renderer SHALL translate these references into Kanka mentions.

Kanka's advanced mention syntax uses forms such as `[entity:123]` and `[entity:123|Alex]`.

On import, recognized Kanka references SHOULD be translated back into local references.

Unsupported Kanka mention syntax MUST be preserved rather than discarded.

---

# 19. Markdown and HTML

Repository prose SHALL use Markdown as its normal authoring format.

Kanka's API uses HTML content for entry bodies and posts.

Therefore the synchronizer SHALL maintain:

```text
Markdown
   ↓
deterministic renderer
   ↓
Kanka HTML
```

and:

```text
Kanka HTML
   ↓
deterministic importer
   ↓
Markdown
```

Round-tripping MUST be tested.

If HTML cannot be represented losslessly in the supported Markdown subset, the importer MUST preserve it as raw HTML rather than silently simplifying it.

Formatting-only transformations SHOULD normalize away so they do not produce perpetual Git diffs.

---

# 20. Normalization

Every resource SHALL have a canonical normalized representation.

Normalization SHOULD cover:

* line endings;
* trailing whitespace;
* deterministic YAML formatting;
* ordering of unordered collections;
* HTML formatting generated by the Markdown renderer;
* null versus missing values where semantically equivalent;
* tag ordering;
* equivalent Kanka reference syntax.

Normalization MUST happen before diff generation.

The following invariant is required:

```text
push
fetch
diff
```

with no intervening human edit MUST produce no semantic changes.

---

# 21. Entity file format

A normal entry might resemble:

```yaml
---
id: prince-maximilian
name: Prince Maximilian

category: character
type: Prince of Cumbria

publish: true

visibility:
  private: false

tags:
  - cumbria
  - nobility

fields:
  title: Prince
  location: house-aldren
---

Prince Maximilian is the surviving claimant to the Cumbrian throne.

## History

...
```

Kanka-specific numeric IDs SHOULD NOT appear here.

---

# 22. Publication safety

New local entities MUST NOT automatically become visible in Kanka.

A new locally created object SHOULD default to:

```yaml
publish: false
```

Publishing requires:

```yaml
publish: true
```

or an explicit command such as:

```bash
git kanka publish prince-maximilian
```

This prevents an unpublished GM note from accidentally becoming player-visible merely because it resides under a synchronizable directory.

---

# 23. Visibility and permissions

Visibility and permissions are security-relevant data and MUST NOT be treated as cosmetic metadata.

Kanka supports entity permissions for actions including Read, Edit, Add, Delete, Posts and Permissions, assigned to campaign roles or individual users.

The synchronizer MUST:

* preserve existing permissions unless explicitly managing them;
* display permission changes prominently;
* never silently reduce privacy;
* never infer permissions from directory names alone;
* avoid changing permissions as a side effect of updating lore.

Permission management SHOULD initially be opt-in.

---

# 24. Properties

Properties SHALL be stored separately from prose where practical.

Example:

```yaml
population:
  name: Population
  type: number
  value: 850000
  private: false

government:
  name: Government
  type: text
  value: Industrial Council
  private: false
```

Kanka properties are independently addressable resources and expose their own creation/update metadata.

Therefore they SHOULD be diffed and synchronized independently from the main entry body.

---

# 25. Posts

Posts SHALL normally be individual files:

```text
posts/
├── public-history.md
├── alice-journal.md
└── gm-notes.md
```

Post metadata SHOULD include:

```yaml
id: alice-journal
name: Alice's Journal
visibility: self
```

Kanka posts have independent CRUD operations, visibility, creator/updater information and permissions.

This isolation reduces merge conflicts between GM and player material on the same entity.

---

# 26. Relations

Relations SHOULD use local IDs:

```yaml
- id: maximilian-house-aldren
  target: house-aldren
  relation: sheltered by
  attitude: 40
  visibility: admin
```

Kanka exposes relations as independent resources with owners, targets, visibility and CRUD operations.

The synchronization layer SHALL resolve local IDs into Kanka entity IDs.

---

# 27. Unsupported Kanka resources

Kanka entities can have related resources including properties, reminders, files, mentions, tags, relations, inventory, abilities, links and posts.

A resource MUST NOT become write-managed until its round-trip behavior is understood and tested.

Unsupported resources SHALL follow this rule:

> **Preserve, observe, never destroy.**

A push MUST NOT delete a remote resource merely because that resource has no representation in the current repository schema.

---

# 28. Resource support levels

Every adapter SHALL declare one of:

```text
FULL
READ_ONLY
UNMANAGED
```

**FULL**
: The project can import, diff, create, update and deliberately delete the resource.

**READ_ONLY**
: The project imports it for awareness but will not modify it.

**UNMANAGED**
: Kanka owns it completely. Sync operations must leave it untouched.

Production code MUST NOT assume that absence from Git means deletion from Kanka.

---

# 29. Conflict granularity

Resources SHOULD be split so unrelated edits do not conflict.

For example:

```text
index.md
properties.yml
relations.yml
posts/alice-journal.md
posts/gm-notes.md
```

is preferred over one giant representation containing all data.

The system SHOULD perform semantic merging of structured YAML fields.

Example:

```text
BASE:
population: 800000
government: Industrial Council

LOCAL:
population: 850000
government: Industrial Council

REMOTE:
population: 800000
government: City Council
```

can safely become:

```text
population: 850000
government: City Council
```

because the edits affect different fields.

---

# 30. Hard conflicts

Automatic resolution is prohibited when both sides alter the same semantic value differently.

Example:

```text
BASE:
government: Industrial Council

LOCAL:
government: Directorate Council

REMOTE:
government: Tarant City Council
```

The synchronizer MUST produce a conflict.

It MUST NOT prefer LOCAL merely because the GM authored it.

It MUST NOT prefer REMOTE merely because it is newer.

The GM decides the resulting world state.

---

# 31. Conflict rules

The following rules SHALL apply:

```text
LOCAL edit + REMOTE unchanged
→ LOCAL wins for next publication

LOCAL unchanged + REMOTE edit
→ REMOTE is available for integration

different structured fields changed
→ automatic merge allowed

same structured field changed differently
→ conflict

prose changed on both sides
→ normal three-way merge

delete + edit
→ always conflict

visibility changed on both sides
→ always conflict

permissions changed
→ review required

unknown authorship
→ treat conservatively as external
```

---

# 32. Deletions

Deletion SHALL be intentionally difficult.

Removing a file from the working tree MUST NOT, by itself, delete the corresponding Kanka object.

A remote deletion MUST be imported into `kanka/live` and presented for review.

A local Kanka deletion SHOULD require an explicit tombstone:

```yaml
deleted: true
```

or an explicit command:

```bash
git kanka delete prince-maximilian
```

The intended deletion then appears in the push plan.

Kanka warns that API changes affect live data immediately and that recovery is limited to eligible resources/campaigns rather than being a substitute for backups.

For that reason, destructive operations SHALL be applied last during a push.

---

# 33. Push transaction ordering

A push SHOULD execute approximately in this order:

```text
1. Create new entities.
2. Record returned Kanka IDs.
3. Resolve local cross-references.
4. Update existing entity fields.
5. Update prose.
6. Update tags.
7. Update properties.
8. Update posts.
9. Update relations.
10. Apply explicitly managed permissions.
11. Perform explicitly approved deletions.
12. Refetch.
13. Verify.
```

This ordering allows newly created entities to be referenced by other changes in the same publication operation.

---

# 34. Partial push failure

A Kanka push cannot be assumed to be transactionally atomic.

If an operation fails partway through:

* remaining dependent operations MUST stop;
* successful operations MUST be recorded;
* the synchronizer MUST refetch Kanka;
* it MUST reconstruct the true remote state;
* it MUST NOT blindly replay the entire transaction.

Recovery is state-based, not assumption-based.

---

# 35. Idempotence

Every operation SHALL be designed to be idempotent at the synchronization level.

Running:

```bash
git kanka push
```

twice without changes SHOULD result in the second run performing no write operations.

Running:

```bash
git kanka fetch
```

twice without Kanka changes SHOULD create no second Git commit.

---

# 37. `git kanka status`

Status SHOULD distinguish source and authorship:

```text
Kanka Git Sync

REMOTE CHANGES

  Player: Alice
    M characters/elizabeth-rowan/posts/journal.md

  Player: Bob
    M locations/tarant/properties.yml

```

# 38. `git kanka plan`

Because Kanka has no API dry-run facility, the project SHALL provide its own local planning mode before sending writes. Kanka itself explicitly states that write/delete requests affect live data.

Example:

```text
PUSH PLAN

CREATE
  location: Seabreak Chapel

UPDATE
  Prince Maximilian
    entry
    type

  Psychodynamics
    entry

CREATE RELATION
  Prince Maximilian → House Aldren
  "sheltered by"

DELETE
  none

PERMISSION CHANGES
  none

3 entities affected.
5 API mutations planned.
```

---

# 39. Validation

`git kanka validate` MUST run without contacting Kanka where possible.

It SHOULD detect:

* duplicate local IDs;
* broken `[[references]]`;
* references to deleted entities;
* invalid YAML;
* unknown entity categories;
* unsupported visibility values;
* missing required metadata;
* attempted publication of local-only content;
* ambiguous tag references;
* relation targets that do not exist;
* accidental Kanka numeric references in normal prose;
* unrecognized synchronization schema versions.

Validation failure MUST block push when it can cause data corruption.

---

# 40. Secrets

Kanka personal access tokens are bearer credentials. Current Kanka documentation states that they expire after 365 days and should be stored in an environment variable or secrets manager rather than source control.

The token MUST therefore be provided through something such as:

```text
KANKA_TOKEN
```

The token MUST NOT appear in:

```text
config.yml
Git history
logs
URLs
screenshots
error reports
generated debug bundles
```

`.env` files MUST be excluded through `.gitignore`. The synchronizer supports an ignored `.env` in the world repository root, using `KANKA_TOKEN` or `KANKA_API_TOKEN`. Nonblank shell values override file values; within each source, `KANKA_TOKEN` takes precedence. Tokens MUST NOT be written to other configuration files or diagnostics.

---

# 41. API limits

The client MUST implement rate limiting.

Kanka currently documents a limit of 30 authenticated requests per minute by default and 90 requests per minute for subscribers, applied per Kanka user. A `429 Too Many Requests` response should cause the client to slow down rather than retry immediately.

The synchronizer SHOULD:

* minimize unnecessary API calls;
* use bulk APIs where appropriate;
* cache immutable mappings;
* respect `429`;
* use exponential or server-guided backoff;
* avoid polling aggressively.

---

# 42. Testing campaign

Development MUST NOT initially target the production campaign.

Kanka explicitly recommends using a disposable campaign when testing create, update and delete requests because API writes operate on live data.

A dedicated synchronization test campaign SHOULD be created.

Representative fixtures SHOULD include:

```text
character
location
organisation
tag
property
post
relation
private entity
player-editable entity
GM-only entity
cross references
```

---

# 43. Round-trip testing

Every FULL resource type MUST pass:

```text
Kanka
 ↓ import
Git representation
 ↓ publish
Kanka
 ↓ import
Git representation
```

The final normalized Git representation MUST equal the first.

Formally:

```text
normalize(import(publish(import(Kanka))))
==
normalize(import(Kanka))
```

A resource type that fails this property cannot be classified as FULL.

---

# 44. Initial import

The first production import SHALL:

1. Fetch all supported campaign resources.
2. Build `.kanka/ids.yml`.
3. Generate the repository representation.
4. Create `kanka/live`.
5. Create `main` from that exact state.
6. Verify that `main` and `kanka/live` are semantically identical.
7. Run validation.
8. Perform a zero-change push plan.

The expected result of the first plan is:

```text
0 creates
0 updates
0 deletes
```

Until that condition is achieved, write synchronization is not ready for production use.

---

# 45. Kanka history is supplemental

Kanka's own history SHALL NOT be the synchronization database.

Kanka retains general create/update/delete/restore history for 90 days. Premium campaigns can expose previous values for 30 days, but Kanka states that this detailed history does not cover subordinate elements such as properties and articles.

Git therefore remains the permanent historical system.

Kanka history MAY be used for diagnosis and recovery assistance.

---

# 46. AI editing rules

AI tools MAY edit the repository.

They SHALL follow the same workflow as a human IDE user:

```text
AI proposes file changes
        ↓
git diff
        ↓
human review
        ↓
commit
        ↓
normal synchronization
```

AI tooling MUST NOT bypass the synchronization safety rules by writing directly to Kanka when working on the Git-managed world.

This keeps the review boundary:

```text
AI
 ↓
working tree
 ↓
Git review
 ↓
main
 ↓
Kanka
```

---

# 47. Local-only material

The repository MAY contain material that must never reach Kanka.

Recommended mechanisms:

```text
gm/
drafts/
research/
```

or explicit metadata:

```yaml
publish: false
```

The synchronization system MUST use an allowlist-oriented publication model.

It is safer for an unknown new file to remain unpublished than for an unknown file to become public.

---

# 48. Compatibility rule

The repository's world model MUST remain usable without Kanka.

A future exporter should be able to take:

```text
world/
```

and publish it to another system without needing to reinterpret hundreds of Kanka IDs embedded throughout the prose.

Therefore:

* Kanka IDs belong in `.kanka/`;
* world identities belong in world data;
* Kanka syntax belongs in the adapter;
* Markdown remains readable without the synchronizer.

Kanka is a frontend and collaboration platform, not the ontology of the setting.

# 50. Development phases

## Phase 0 — Read-only importer

Goal:

```text
Kanka → Git
```

No Kanka writes.

Success criterion:

The campaign can be browsed comfortably in an IDE without losing relevant data.

## Phase 1 — Deterministic round trip

Implement normalization, Markdown conversion, IDs and references.

Success criterion:

Import → export → import produces no semantic diff.

## Phase 2 — Safe push

Implement:

```text
validate
plan
push
verify
```

Only non-destructive create/update operations.

Implement:

# 51. Definition of production readiness

The synchronizer is not production-ready until all of the following are true:

```text
✓ Existing campaign imports successfully.
✓ Zero-change push produces zero writes.
✓ Player edit appears on kanka/live.
✓ Player edit cannot be overwritten by git kanka push.
✓ Owner Kanka edit can be imported.
✓ Local Git edit can be published.
✓ Non-overlapping concurrent edits merge.
✓ Overlapping edits generate a conflict.
✓ New entity receives and retains stable IDs.
✓ Cross references survive round-trip.
✓ Posts survive round-trip.
✓ Properties survive round-trip.
✓ Relations survive round-trip.
✓ Private content remains private.
✓ Unmanaged resources survive pushes untouched.
✓ Interrupted pushes recover by refetching.
✓ Token never appears in logs or Git.
✓ Deletion requires explicit intention.
```

# 52. Primary project invariant

If only one rule survives future redesigns, it SHALL be this:

> **No synchronization operation may destroy a change made by a human without first making that change visible and requiring an explicit decision about it.**

That includes the GM.

It includes players.

It applies regardless of whether the change originated in Git or Kanka.

Everything else in the architecture exists to make that rule enforceable.
